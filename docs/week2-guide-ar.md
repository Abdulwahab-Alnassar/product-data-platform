# دليل الأسبوع الثاني — Product Data Platform

هدف الأسبوع: تشغيل خط بيانات يمكن متابعة تنفيذه، وفحص جودته،
وتحديث قاعدة بياناته، واختباره تلقائيًا.

## قبل القراءة

نفّذ داخل مجلد المشروع، بعد تفعيل البيئة:

```powershell
git pull origin main
python -m pip install -r requirements.txt
python -m pytest -v
python -m src.pipeline
python -m src.analyze_data
```

الأمر الرابع يعتمد على وجود `data/raw/amazon.csv` عندك.
للتجربة دون استخدام بياناتك الكاملة، استخدم:

```powershell
python -m src.pipeline --input data/sample/amazon_sample.csv --output-dir data/processed/demo
python -m src.analyze_data --database data/processed/demo/products.db
```

هذا يضع مخرجات التجربة كلها داخل `data/processed/demo`.

## اليوم الأول: جمع المراحل

ابدأ بقراءة [src/pipeline.py](../src/pipeline.py).

الدالة `run_pipeline` تقرأ الملف، وتنظّفه، وتجهز المنتجات الفريدة،
وتفحص الجودة، وتحفظ الملفات، ثم تحمّل قاعدة البيانات.
الدالة `main` تستقبل خيارات سطر الأوامر وتعرض ملخص التشغيل.

`python -m src.pipeline` يعني تشغيل الملف باعتباره جزءًا من حزمة
المشروع، لذلك ننفذه من المجلد الرئيسي.

## اليوم الثاني: Logging ومعالجة الفشل

اقرأ [src/logging_utils.py](../src/logging_utils.py)، ثم ارجع إلى
استخدامات `LOGGER` في `pipeline.py`.

- `INFO`: مرحلة بدأت أو عدد سجلات أو عملية اكتملت.
- `WARNING`: حالة تستحق المراجعة، لكنها لا تمنع التحميل.
- `exception`: يسجل الخطأ وتفاصيله ثم نعيد رفع الاستثناء لإيقاف التشغيل.

`perf_counter` يقيس مدة التنفيذ. والسجل الافتراضي في
`logs/pipeline.log` يظهر التاريخ والمستوى والرسالة.
يدور الملف عند بلوغ نحو مليون بايت مع الاحتفاظ بثلاث نسخ سابقة.
تُغلق مقابض الملفات بعد التشغيل، ولا تتراكم handlers مع تكرار `main`.

جرّب مثال الفشل دون لمس قاعدة بياناتك الأساسية:

```powershell
python -m src.pipeline --input missing.csv --output-dir data/processed/failure-demo
```

المتوقع خروج بخطأ وتسجيله في `data/processed/failure-demo/pipeline.log`.
هذا فشل متعمد للتعلم.

## اليوم الثالث: تقرير جودة البيانات

اقرأ [src/validate_data.py](../src/validate_data.py).

`build_quality_report` ينشئ قاموسًا يحتوي على الفحوصات وأعداد المشاكل.
`save_quality_report` يحفظه بصيغة JSON.
`require_quality` يوقف التحميل إذا فشل فحص إلزامي.

أمثلة:

| الحالة في البيانات الجاهزة للتحميل | النتيجة |
| --- | --- |
| معرف منتج فارغ أو مكرر | خطأ يوقف التحميل |
| سعر بعد الخصم أكبر من السعر الأصلي | خطأ يوقف التحميل |
| تقييم خارج 0–5 أو قيمة غير محدودة | خطأ يوقف التحميل |
| عدد تقييمات كسري | خطأ يوقف التحميل |
| تقييم مفقود | تحذير، وتبقى القيمة مفقودة |
| وجود عمود user_id أو user_name | خطأ يوقف التحميل |

التنظيف قد يحوّل قيمة غير صالحة إلى قيمة مفقودة قبل التحقق؛
لذلك قد تظهر كتحذير نقص في التقرير. لا نضع صفرًا مكان تقييم غير معروف.

التقرير يفحص المنتجات الفريدة التي سنحمّلها. وقد يحتوي الملف النظيف
الوسيط على عدة صفوف للمنتج نفسه قبل اختيار صف واحد.
فشل الجودة يكتب تقريرًا تشخيصيًا، لكنه لا يغيّر CSV المنتجات أو قاعدة البيانات.
أما فشل مبكر مثل غياب الملف، فقد يحدث قبل إنشاء التقرير؛ راجع السجل.

## اليوم الرابع: Upsert والمعاملات

اقرأ [src/load_to_db.py](../src/load_to_db.py)، خصوصًا `load_database`.

سابقًا كنا نحذف محتوى جدول المنتجات ثم نعيد إدخاله.
الآن نستخدم `ON CONFLICT(product_id) DO UPDATE`:

- معرف جديد: إضافة.
- معرف موجود: تحديث قيمه بالقيم القادمة.
- منتج غير وارد في الدفعة: يبقى في القاعدة.

مثال: القاعدة فيها P1 وP2. وصلت دفعة فيها P1 بسعر جديد.
نحدّث P1، ويبقى P2. عدد الدفعة 1، وعدد القاعدة 2؛ وهذا نجاح.

القيم المفقودة الجديدة تستبدل القديمة أيضًا. ليست لدينا تواريخ تحديث
للمقارنة، لذلك الدفعة التي ترسلها تُعامل باعتبارها المصدر المعتمد.

الجدول المؤقت `batch_products` يسمح بمقارنة القيم الواردة بالمخزنة،
بما فيها NULL، قبل تثبيت المعاملة. فشل صف يعيد تغييرات منتجات الدفعة
كلها إلى ما كانت عليه. هذه المعاملة تخص SQLite؛ ملفات CSV والتقرير
ليست ضمن المعاملة نفسها.

عندما يتكرر معرف داخل الدفعة، تختار `prepare_data` الصف الذي
له أعلى `rating_count`. عند التعادل، تحتفظ بأول صف.

## اليوم الخامس: Views وWindow Functions

اقرأ بالترتيب:

1. [sql/views.sql](../sql/views.sql)
2. [sql/advanced_queries.sql](../sql/advanced_queries.sql)
3. [src/analyze_data.py](../src/analyze_data.py)

الـView استعلام محفوظ نستخدمه كأنه جدول؛ لا ينسخ البيانات.
`product_analytics` يحسب مقدار التوفير، والفئة الرئيسية،
ومستوى التقييم، وعدد الحقول الرقمية المفقودة.

`category_product_rankings` يرتب التقييمات داخل كل فئة.
`PARTITION BY` يقسم المنتجات إلى مجموعات،
و`DENSE_RANK` يعطي التقييمات المتساوية الرتبة نفسها.
مثلًا: 4.8 و4.8 و4.5 تصبح رتبها 1 و1 و2.

الأسعار في هذه البيانات **بالروبية الهندية INR، وليست بالريال**.
الحساب يطرح السعر المخفض من الأصلي دون تحويل عملة.

أداة التحليل تقرأ قاعدة البيانات فقط، وتنفذ الاستعلامات الخمسة
المتقدمة وتعرض نتائجها. شغّل الـPipeline الجديد أولًا لإنشاء الـViews.

## اليوم السادس: GitHub Actions

اقرأ [.github/workflows/tests.yml](../.github/workflows/tests.yml).

بعد push أو pull request، يقوم GitHub بالآتي:

1. يجلب الكود.
2. يجهز Python 3.12.
3. يثبت المتطلبات.
4. يشغّل Pytest.
5. يشغّل الـPipeline على العينة المنشورة داخل مجلد منفصل.
6. ينفّذ SQL التحليلي.

ينفذ ذلك على Ubuntu وWindows. بياناتك الكاملة غير مطلوبة.
شاهد النتيجة من تبويب Actions أو الشارة الموجودة في README.
ظهور نجاح الاختبارات لا يثبت خلو المشروع من كل عيب؛ بل يثبت
أن الحالات التي اختبرناها تعمل على ذلك الإصدار.

## اليوم السابع: مراجعة وفهم

اقرأ [tests/test_week2.py](../tests/test_week2.py) بعد الملفات السابقة.
اختبارات صغيرة توضح السلوك المطلوب من كل مكوّن.

قبل الانتقال للأسبوع الثالث، جرّب الإجابة:

- لماذا قد يختلف عدد منتجات الدفعة عن العدد الكلي في القاعدة؟
- ما الفرق بين خطأ الجودة والتحذير؟
- ماذا يحدث للمنتجات غير الموجودة في الدفعة الجديدة؟
- ما حدود معاملة SQLite؟ هل تشمل ملفات CSV؟
- لماذا قد تعطي أعلى ثلاث رتب أكثر من ثلاثة منتجات؟
- أين تراجع تفاصيل فشل التشغيل؟

يكفي أن تشرح الفكرة بكلامك، ولا تحتاج تحفظ الكود.
الأسبوع الثالث مخصص للانتقال إلى PostgreSQL وDocker؛
لم نضفهما ضمن هذا الأسبوع.
